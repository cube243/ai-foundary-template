# ADR-0009: コスト集計はAthena、レイテンシ/エラー率はCloudWatch Logs Insightsという指標ごとの置き場所を分ける

## ステータス
承認済み

## コンテキスト
運用上必要な可観測性には性質の異なる2種類の分析ニーズがある。1つは「このテナントに今月いくら課金すべきか」のようなコスト集計で、Bedrock Model Invocation Loggingの`requestMetadata`のような詳細な課金関連データを長期間・大量に蓄積し、SQLで柔軟に集計する必要がある。もう1つは「このリクエストは何ミリ秒かかったか、エラーだったか」のような運用監視で、直近のログに対して素早くクエリを投げ、ダッシュボードやアラートに使う必要がある。

## 決定
コストの集計はBedrock Model Invocation Logging(requestMetadata経由)→S3+Glue+Athenaという経路を想定する。レイテンシ・エラー率の分析はCloudWatch Logs Insightsで行う想定とする。ただし、本テンプレート単体の実装範囲は「ログを正しい形(3.8の構造化ログスキーマ)で出す」ところまでとし、Athena/Glueのリソース自体(データベース、クローラ、テーブル定義等)は共通モニタリング基盤側の責務として本テンプレートには含めない。

## 検討した代替案
- **本テンプレート単体でAthena/Glueまで含めて完結させる**: テンプレートごとにGlueデータベース・クローラ・Athenaワークグループが重複して作られることになり、コスト集計を横断的に行いたいという本来の目的(複数エージェント/複数テンプレートを横断したコスト可視化)と矛盾する。コスト集計基盤は本質的に複数テンプレートにまたがる共通基盤であるべきで、これは指示書内でも「もし本テンプレート単体で完結させる必要があれば質問すること」と明記されていたが、今回はテンプレート単体スコープ外という指示書の想定通りに進めた。
- **レイテンシ/エラー率もAthena経由で集計する**: 運用監視のように低レイテンシ・即応性が求められる用途にはAthenaのクエリ実行時間は不向きであり、CloudWatch Logs Insightsの方が適している。

## 結果・トレードオフ
得られるもの: 本テンプレートの実装範囲が明確になり、Athena/Glueという別の意思決定(パーティション設計、クローラのスケジュール、コスト配分タグ設計等)を本テンプレートが背負わずに済む。
引き換えに受け入れるもの: 本テンプレートを単独でデプロイしただけでは、コスト集計の仕組みは動かない。共通モニタリング基盤(本リポジトリの将来のスコープ、または利用者側の既存基盤)が別途Athena/Glueを用意することが前提になる。
