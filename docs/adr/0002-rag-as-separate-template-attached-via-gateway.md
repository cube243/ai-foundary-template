# ADR-0002: RAGを単一テンプレートにせず、tool-agentと後から組み合わせる方式にした

## ステータス
承認済み

## コンテキスト
RAG機能(ベクトル検索)は多くの場合エージェント(`templates/tool-agent`)とセットで使われる。素朴には両者を1つの結合されたテンプレートとして提供する案もあったが、ADR-0001で決めた「テンプレートの完全独立・依存ゼロ」の原則と両立させる必要があった。加えて、Amazon Bedrock AgentCore Gatewayには、Lambda ARNをツールターゲットとして後付けでアタッチできる仕組みがあり、エージェント側とツール側を疎結合に保てる技術的な前提が既に存在する。

## 決定
RAGは`templates/rag-vector-db-bedrock-kb`という独立したテンプレートとして提供する。利用者は`templates/tool-agent`と`templates/rag-vector-db-bedrock-kb`を別々にcookiecutterし、後から`rag-vector-db-bedrock-kb`が出力する`query_document`のLambda ARNを、AgentCore Gatewayにツールとしてアタッチすることで両者を組み合わせる。この組み合わせ方は`rag-vector-db-bedrock-kb/README.md`に明記する。

## 検討した代替案
- **1つの結合テンプレート(agent+RAGを同梱)**: ADR-0001の「完全独立」原則に反する。また、RAGを必要としないエージェントや、複数のRAGバックエンドを使い分けたいケースに対応できず、テンプレートの組み合わせ数が組み合わせ爆発を起こす。
- **RAG側がtool-agent側のTerraform stateやリソースを`data`ソースで参照する**: 疎結合に見えるが、実質的には「どちらのテンプレートを先にapplyするか」という順序依存が生まれ、単独コピーして使えるという前提が崩れる。

## 結果・トレードオフ
得られるもの: RAGを使わないエージェント、複数のRAGバックエンドを使い分けたいエージェント、RAGだけを他の用途(バッチ処理からの検索等)に使うケースのいずれにも、テンプレートの組み合わせを増やさずに対応できる。
引き換えに受け入れるもの: 「Gatewayのツールとして後付けでアタッチする」という統合作業そのものは、このテンプレート単体のTerraformでは自動化されない(利用者またはtool-agent側の責務)。特に、Gatewayが検証済みJWTクレーム(tenant_id)をLambdaターゲットの呼び出しコンテキストに伝播する標準的な仕組みが無いため、テナント分離を安全に機能させるにはGateway側にリクエストインターセプターを別途構成する必要があり、これは本テンプレートの実装時点で未解決のTODOとしてREADMEに明記している。
