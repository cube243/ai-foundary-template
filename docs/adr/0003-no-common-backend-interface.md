# ADR-0003: バックエンド間の共通インターフェース・契約テストを採用しない

## ステータス
承認済み

## コンテキスト
`rag-vector-db-bedrock-kb`は現時点でBedrock Knowledge Basesのみを実装しているが、将来的に`templates/rag-vector-db-opensearch`のような別バックエンドのテンプレートが追加される可能性がある。複数バックエンドが並立する設計では、一般的にPort/Adapterパターンのような共通インターフェースと、それを保証する契約テスト(contract test)基盤を用意することが検討される。本プロジェクトでもこれを一度検討した。

## 決定
バックエンド差し替えのための共通インターフェース強制の仕組み(Port層・契約テストのようなコードレベルの基盤)は採用しない。関数名・入出力の型といった「緩やかな命名一貫性」のみを各テンプレート間で揃えることとし、それ以上の強制は行わない。

## 検討した代替案
- **共通Port層+契約テスト基盤**: 一度検討したが、バックエンドの選択は「利用者がcookiecutterするテンプレートフォルダを選ぶ」という一度きりの人間の意思決定であり、実行時にバックエンドを動的に差し替える必要が無い。契約テストが本来価値を発揮するのは「同一インターフェースの実装を実行時に切り替える/両方を同時に運用する」ような状況であり、本プロジェクトの利用形態には当てはまらない。
- **共通Terraformモジュールで抽象化**: ADR-0001の「完全独立」原則と衝突する。

## 結果・トレードオフ
得られるもの: 契約テスト基盤・Port層の設計/保守コストがゼロになる。各テンプレートは自分のバックエンドに最適な形でLambda関数やTerraformリソースを自由に設計できる(例: Bedrock KB版は`document_id`をBedrock側の制約に合わせて`{tenant_id}::{document_id}`という合成キーにする、といったバックエンド固有の工夫がしやすい)。
引き換えに受け入れるもの: 将来複数のバックエンドテンプレートが並立したとき、関数のシグネチャや細部の挙動(エラーレスポンスの形、非同期/同期の粒度など)が完全には揃わない可能性がある。これは許容し、必要になった時点で個別に足並みを揃える。
