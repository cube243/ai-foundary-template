# ADR-0006: テナント分離をプール型(共有DB+メタデータフィルタ)にし、サイロ型を例外的なエスカレーション手段とする

## ステータス
承認済み

## コンテキスト
マルチテナントのRAGバックエンドでは、テナントごとにデータをどう分離するかが重要な設計判断になる。代表的な方式として、全テナントで1つのKnowledge Base(ベクトルインデックス)を共有し、メタデータでフィルタする「プール型」と、テナントごとに個別のKnowledge Baseを作る「サイロ型」がある。

## 決定
デフォルトはプール型とする。1つのKnowledge Baseを全テナントで共有し、各文書に`tenant_id`メタデータを付与、検索時は`filter`で強制的に絞り込む(ADR-0004)。サイロ型はデフォルトでは実装しないが、`variables.tf`に「大口顧客の契約上の要求、または性能分離が必要な場合はサイロ型への切り替えを検討する」旨のコメントを残し、将来のエスカレーション手段として明記する。

## 検討した代替案
- **最初からテナントごとにKnowledge Baseを作るサイロ型をデフォルトにする**: テナント数に比例してKnowledge Base・データソース・IAMロール等のインフラが増加し、テンプレートとしての運用コストとTerraformの複雑さが増す。契約上の分離要求や性能分離が必要になるテナントは一部に限られると想定され、全テナントに対してこのコストを負わせる必要は無いと判断した。
- **テナントごとにS3 Vectorsのインデックスだけを分け、Knowledge Base自体は共有する**: 検討したが、Bedrock Knowledge Base自体がテナントの実質的な分離境界になっていないと、IAMロールや同時実行数上限(アカウント全体で共有)といった他の制約の管理が複雑になる。ADR-0005で選んだCUSTOMデータソース+メタデータフィルタの構成と比べて明確な利点が無い。

## 結果・トレードオフ
得られるもの: テナント数が増えてもインフラの数はO(1)のまま(Knowledge Base、データソース、S3 Vectorsインデックスはそれぞれ1つ)。新規テナントのオンボーディングにインフラ変更が不要。
引き換えに受け入れるもの: 全テナントが同じKnowledge Base/S3 Vectorsインデックス/Bedrockのアカウント全体の同時実行数枠を共有するため、性能面・契約面でのテナント間分離は弱い。あるテナントの利用量が突出すると他のテナントに影響しうる(この影響を緩和するテナント単位レート制限は、今回の実装スコープからは除外している — README参照)。契約上または性能上の理由でより強い分離が必要になったテナントは、サイロ型への個別移行(この判断の一部として`variables.tf`にコメントを残した拡張ポイント)で対応する。
